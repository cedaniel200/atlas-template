# OpenSpec pipeline

## Phases

```
explore → propose (proposal, specs, design, adr, tasks) → apply → QA → review → archive
```

### Artifact order

`proposal → specs → design → adr → tasks`

Each artifact is written only when its dependencies are complete and the user approves it.

### Rules

- **The user runs the OpenSpec commands**; the agent says which command and what to review.
- **The user reviews each artifact** before moving to the next one.
- **Command syntax depends on the host**: the wrappers are generated by
  `openspec init/update --tools <host>`.
- **Never proceed without explicit approval.**

## Phases in detail

### 1. Explore

Think, ask, visualize. Do not implement. If the idea crystallizes, propose a change.

### 2. Propose

Generate proposal, specs, design, adr and tasks. Add `qa-scenarios.md` when the change has an
end-to-end flow worth testing.

### 3. Apply

TDD per task: red → green → refactor → commit. Run the project's quality gate before closing.

### 4. QA

Scenario inventory → gap analysis → execution. Approval requires `-FINAL` with zero open high-severity
findings.

### 5. Consistency checkpoint

Before QA: does the code implement the approved design? Did the scope change? Are the new ADRs
coherent? If there is drift, fix the design **before** spending QA and review iterations.

### 6. Review

Code review against the declared architecture and security, plus quantitative gates. No critical
findings and highs resolved → `-FINAL`.

### 7. Archive

`openspec archive <change>` and sync the specs. Commit `chore: archive <change>`.

## Limits

- Maximum 5 iterations between QA and review.
- If QA reports `BLOQUEADO` (3+ high findings on the second iteration), return to design with the user.
- No finding is closed silently: it is fixed or documented with the user's approval.
